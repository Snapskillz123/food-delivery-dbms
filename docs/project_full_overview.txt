1. PROJECT PURPOSE
------------------

This project is a database-first food-delivery platform inspired by Swiggy and
Zomato. It supports customers, reusable addresses, restaurants, categorized
menus, multi-item orders, coupons, payments, delivery agents, status tracking,
restaurant reviews, delivery reviews, and operational analytics.

The primary purpose is to demonstrate DBMS engineering rather than frontend
complexity. PostgreSQL is the final integrity boundary, FastAPI coordinates
business workflows, a responsive customer website uses the real REST API, and
Streamlit provides an administrative analytics dashboard.

A food-delivery order is more than CRUD. Prices must remain historically
accurate, items must belong to one active restaurant, coupons have concurrent
usage limits, totals must be trusted, status changes must follow a legal state
machine, agents cannot handle conflicting deliveries, payments may require
refunds, reviews require delivered orders, and all of this data must later
support meaningful analytics.

4. DATABASE SCHEMA
------------------

The database contains 14 tables.

4.1 users

Stores user_id, full_name, unique email, unique phone, password_hash,
created_at, and updated_at. Passwords are bcrypt hashes, never plaintext.
One user can own multiple addresses, place multiple orders, and submit reviews.

4.2 addresses

Stores address_id, user_id, label, address line, city, state, postal code,
coordinates, is_default, and created_at. The order service verifies that the
selected delivery address belongs to the customer. A partial unique index
limits a user to one default address.

4.3 restaurants

Stores restaurant identity, cuisine, contact information, location, cached
rating, active state, opening time, closing time, and created_at. An inactive
restaurant cannot receive an order. The cached rating is recalculated by a
database trigger whenever source reviews change.

4.4 menu_categories

Stores restaurant-scoped categories such as Starters, Main Course, Desserts,
and Beverages. Category names are unique inside a restaurant.

4.5 menu_items

Stores restaurant_id, category_id, name, description, positive price,
vegetarian flag, availability flag, and timestamps. Cross-table database logic
ensures that an item's category belongs to the same restaurant. Unavailable
items cannot be ordered.

4.6 delivery_agents

Stores identity, unique phone and vehicle number, vehicle type, status, cached
average rating, and created_at. Status is AVAILABLE, BUSY, or OFFLINE. Only an
AVAILABLE agent can be assigned. Application locking and a partial unique
index prevent an agent from handling more than one active order.

4.7 orders

The central financial and fulfillment record. It references the customer,
restaurant, address, and optional delivery agent. It stores status, subtotal,
delivery fee, tax, discount, final total, and lifecycle timestamps.

Valid statuses are:

PLACED -> ACCEPTED -> PREPARING -> READY_FOR_PICKUP -> PICKED_UP
       -> OUT_FOR_DELIVERY -> DELIVERED

Cancellation is allowed from PLACED, ACCEPTED, PREPARING, and
READY_FOR_PICKUP. DELIVERED and CANCELLED are terminal states.

The required financial identity is:

total_amount = subtotal + delivery_fee + tax_amount - discount_amount

All financial values must be nonnegative, and the discount cannot exceed the
pre-discount amount.

4.8 order_items

Stores one row per order line: order, menu item, quantity, immutable unit-price
snapshot, and total price. The unit price is copied at checkout so historical
orders remain correct after menu-price changes. A trigger always derives:

total_price = quantity * unit_price

4.9 order_status_history

Stores order_id, previous_status, new_status, and changed_at. An audit trigger
automatically creates the initial PLACED event and every later transition.

4.10 payments

Stores one payment lifecycle per order. Methods are UPI, CARD, CASH, and
WALLET. Statuses are PENDING, SUCCESS, FAILED, and REFUNDED. Successful and
refunded payments are finalized and cannot be overwritten arbitrarily.

4.11 restaurant_reviews

Stores a 1-to-5 rating and optional text for a delivered order. The reviewer
and restaurant must match the order. Only one restaurant review is permitted
per order.

4.12 delivery_reviews

Stores a 1-to-5 rating and optional text for the agent who delivered an order.
The order must be delivered, and only one delivery review is permitted per
order.

4.13 coupons

Supports percentage and fixed discounts, minimum order value, optional maximum
cap, valid-from and valid-until dates, usage limit, usage count, and active
state. Seed examples include WELCOME20, FLAT75, and an expired coupon.

4.14 order_coupons

Junction table connecting an order to a coupon. It stores discount_applied so
the exact historical redemption remains available even if coupon configuration
changes later.


5. NORMALIZATION
----------------

First Normal Form:
Every field is scalar. Repeating groups are separate relations. For example,
an order does not contain a comma-separated menu list; lines are stored in
order_items.

Second Normal Form:
Non-key values depend on the complete key. Most relations use a surrogate
single-column key. In the composite order_coupons relation, discount_applied
depends on the exact order-coupon combination.

Third Normal Form:
Customer facts exist in users, address facts in addresses, restaurant facts in
restaurants, payment state in payments, coupon definitions in coupons, and
review facts in their review tables. Non-key attributes do not depend on other
non-key attributes.

Intentional redundancy:

1. order_items.unit_price is the immutable checkout-price snapshot.
2. order_items.total_price supports invoices and analytical access.
3. Order financial fields preserve the complete invoice snapshot.
4. Restaurant and agent ratings are cached for frequent reads.

Triggers and constraints maintain the correctness of these derived values.


6. TRANSACTIONAL WORKFLOWS
--------------------------

6.1 Place order

The client submits customer ID, restaurant ID, address ID, item IDs and
quantities, payment method, and an optional coupon. It never submits totals.

Inside one SQLAlchemy transaction, the service:

1. Validates that the restaurant exists and is active.
2. Validates that the address belongs to the customer.
3. Rejects duplicate menu-item lines.
4. Loads and validates every requested menu item.
5. Ensures all items belong to the selected restaurant.
6. Ensures all items are available.
7. Calculates the subtotal with Decimal arithmetic.
8. Locks and validates an optional coupon with SELECT FOR UPDATE.
9. Applies date, active-state, usage, minimum-value, type, and cap rules.
10. Calculates 5 percent tax and the default 40-rupee delivery fee.
11. Calculates the final amount.
12. Creates the order.
13. Creates immutable order-item snapshots.
14. Creates a pending payment.
15. Records coupon redemption and increments usage when applicable.
16. Lets the status-history trigger create the initial PLACED event.
17. Commits every write together.

Any failure rolls back the entire operation.

6.2 Cancellation

The service locks the order, validates cancellation eligibility, changes the
status to CANCELLED, records cancelled_time, refunds a successful payment,
releases an assigned agent, lets the audit trigger record the transition, and
commits everything atomically.

6.3 Status progression and delivery completion

Status transitions are validated by both the FastAPI service and PostgreSQL.
When pickup occurs, an agent is required, the agent row is locked, availability
and active assignments are checked, and the agent becomes BUSY. On delivery,
delivered_time is stored and the agent becomes AVAILABLE.

6.4 Payment update

Every order receives one payment record. Pending or failed payments can be
updated. A successful payment receives paid_at. Successful and refunded
payments are finalized. Order cancellation changes a successful payment to
REFUNDED inside the cancellation transaction.


7. ACID PROPERTIES
------------------

Atomicity: Order, lines, payment, coupon use, cancellation, refund, and agent
changes commit as complete units or roll back.

Consistency: Enums, foreign keys, CHECK constraints, UNIQUE constraints,
service rules, and triggers reject invalid states.

Isolation: SELECT FOR UPDATE locks contested orders, coupons, delivery agents,
and payments to reduce conflicting concurrent updates.

Durability: PostgreSQL persists committed data using its transactional storage
and write-ahead logging.


8. POSTGRESQL TRIGGERS
----------------------

- Status-history trigger records order creation and later status changes.
- Transition trigger rejects illegal order-state jumps at database level.
- Restaurant-rating trigger recalculates averages after review changes.
- Agent-rating trigger recalculates averages after delivery-review changes.
- Order-line trigger derives quantity times unit price.
- Financial trigger rejects inconsistent order totals.
- Cross-table validation protects category ownership and delivered-review
  ownership rules.

These rules remain effective even if data is written outside FastAPI.

- The customer website uses seeded user/address IDs.
- PostGIS distance-based delivery is not implemented.
- Restaurant opening hours are displayed but not yet enforced at checkout.
- The application is a portfolio/educational system, not a high-traffic
  production platform.
- Render free services can sleep and have provider lifecycle limitations.
- No Redis, Kafka, Kubernetes, microservices, or cloud-specific complexity was
  added because those would distract from the DBMS objective.


20. INTERVIEW EXPLANATION
-------------------------

Short explanation:

I built a database-first food-delivery management system using PostgreSQL,
FastAPI, SQLAlchemy, Streamlit, and Docker. The 3NF schema covers customers,
addresses, restaurants, menus, multi-item orders, delivery agents, payments,
coupons, reviews, and audited status history. Checkout, cancellation, and
delivery completion are ACID transactions with row-level locking. PostgreSQL
constraints and triggers protect totals, immutable price snapshots, review
eligibility, transitions, ratings, and audit history. The project also includes
stored functions, views, workload-based indexes, 31 analytical queries, 1,200
realistic orders, a customer website, a dashboard, tests, Docker, and a live
Render deployment.

Why use PostgreSQL rules as well as FastAPI?

FastAPI provides understandable workflow errors, while PostgreSQL remains the
final integrity boundary. Invalid totals, transitions, ratings, or cross-table
relationships are rejected even when another client bypasses the API.

Most important transaction:

Checkout validates customer ownership, restaurant state, menu ownership,
availability, and coupon eligibility under locking. It calculates trusted
Decimal totals and creates the order, immutable lines, payment, coupon
redemption, and audit history atomically. Failure rolls back everything.

Normalization versus performance:

The design is in 3NF, with deliberate snapshots for historical financial
correctness and cached aggregate ratings for high-read screens. Triggers keep
the derived values consistent.

Concurrency:

SELECT FOR UPDATE protects orders, coupons, agents, and payments. A partial
unique index adds a final database guarantee against multiple active orders for
one delivery agent.
